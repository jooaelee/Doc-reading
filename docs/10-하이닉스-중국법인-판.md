# 하이닉스 중국법인 판. 줄 단위 추출과 GERP 품목 표

우시와 충칭의 하이닉스 Local 물류팀이 쓸 수 있게 만든 별도 추출 판이다. 우리 판은
KEROL SO 한 행을 채우는 것이 목적이라 줄 단위 값을 최소로 뽑는다. 이 판은 인보이스와
포장명세서의 줄을 통째로 뽑아 GERP 품목 표 모양의 엑셀로 낸다.

만든 것이 셋이다.

| 것 | 자리 |
|---|---|
| 추출 판 `h1` | `tools/docpipe.py` 의 `PROFILES["h1"]` |
| 엑셀 산출기 | `tools/gerp_xlsx.py` |
| 데모 화면 | `tools/hynix_demo.py` |
| 잠금 시험 | `tests/test_docpipe_hynix.py` (23건) |

## 1. 왜 판을 가르나

받는 곳이 다르다. 우리 쪽 산출물은 KEROL SO 업로드 양식 60열이고, 하이닉스는 KEROL 을
쓰지 않는다. 그쪽이 넣는 화면은 GERP 의 「Change Bill of Lading: General1 (China)」 이고,
그 화면 아래쪽 B/L Item Update 표가 BL 에 실린 PO 별 품목을 받는다. 열이 여덟이다.

```
Imp.Req. No. | Item | Purchase Order | Material | Vendor Part No. | B/L quantity | Invoice amount | Net Price
```

한 줄이 PO 에 걸리려면 그 줄에 PO 번호와 품목 코드가 있어야 한다. 우리 판은 건 단위
`customer_po` 에 PO 하나만 담으므로 이 표의 한 줄도 못 채운다. 실제로 인보이스 한 장에
PO 번호가 열 개 넘게 나열되는 서류가 있다(`02-GERP-PO-매핑.md` 4장).

v4 를 그대로 늘리지 않은 이유는 그 판의 「보태는 기준」 때문이다. KEROL 로 가거나 규칙
하나를 새로 세우거나 둘 중 하나여야 칸을 늘린다. 줄 단위 PO 와 자재 코드는 KEROL 로
가지 않는다. 품목이 KEROL 관리 대상이 아니라서다. 우리 판에 넣으면 아무도 안 보는 칸이
늘고 기존 칸의 정확도만 갉는다.

## 2. 사이트마다 값이 다르다

`02-GERP-PO-매핑.md` 3장이 적어 둔 대로다.

| 사이트 | PO 매핑 주체 | 이 판의 값 |
|---|---|---|
| 우시 | 하이닉스 Local 물류팀 | 하이닉스의 공수를 줄인다 |
| 충칭 | 하이닉스 Local 물류팀 | 같다. 다만 물량이 작다 |
| 대련 | FSK (DMTM 상주 인력) | 우리 공수를 줄인다 |

우시와 충칭은 하이닉스가 직접 매핑하므로 이 판은 상대의 일을 대신 해 주는 제안이 된다.
하이닉스 본사가 중국법인까지 서류 파싱을 지원하지 않아 생긴 자리다. 서류는 보안 때문에
직접 못 받으므로, 우리가 가진 같은 구조의 서류로 만들어 보여 준다.

## 3. 늘어난 칸

줄마다 받는 칸이다. 인보이스 줄과 포장명세서 줄에 같이 붙인다.

| 칸 | 어디서 | 왜 |
|---|---|---|
| `invoice_no` | 그 줄이 실린 인보이스 번호 | 한 묶음에 인보이스가 네 장 오는 서류가 있다 |
| `seq` | 표 첫 열의 줄 번호 | 인보이스마다 1 부터 다시 센다 |
| `sap_code` | Sap Code 열 | |
| `po_no` | Po No. 열 | GERP 의 Purchase Order |
| `po_item_no` | Po Item No. 열 | GERP 의 Item |
| `iv_no` | SK Hynix I/V No. 열 | |
| `hios_no` | HIOS No. 열 | |
| `material_code`, `part_no` | 위 다섯 열이 하나도 안 찍힌 서류에서만 | 열 이름이 다른 공급사 |
| `unit`, `hs_code`, `country_of_origin` | 줄에 찍혀 있으면 | |
| `case_no`, `net`, `gross` | 포장명세서 줄 | |

건 단위로 둘을 더 받는다. `po_list` 는 묶음 어디에든 찍힌 PO 번호 전부이고,
`invoice_totals` 는 인보이스마다 번호와 총액과 통화다.

### 뜻을 붙이지 않는다

처음에는 `material_code` 와 `part_no` 두 칸에 뜻을 붙여 받았다. 실제 서류를 열어 보니
코드 열이 다섯이었다. 다섯 중 어느 것이 GERP 의 Material 인지는 서류만 보고 정할 수
없고 하이닉스가 정한다. 우리가 뜻을 붙이면 그 판단을 우리가 대신한 것이 되고, 틀리면
틀린 코드가 ERP 로 들어간다.

그래서 추출은 인쇄된 이름 그대로 받고, GERP 열로 잇는 일은 `tools/gerp_xlsx.py` 의
`GERP_MAP` 한 자리에서 한다. 다섯 열을 표에 그대로 같이 실어서 상대가 눈으로 확인할
수 있게 했다. 「Material 은 I/V No. 입니다」 라는 답을 받으면 표의 한 줄만 고친다.

## 4. 고친 자리가 프롬프트가 아니라 입력이었다

처음 돌렸을 때 모델이 인보이스마다 열을 다르게 짚었다. 1장은 Sap Code 자리에 A 를
넣고 2장은 같은 자리에 B 를 넣는 식이다. 프롬프트를 좁혀도 안 고쳐졌다.

원인은 글에 있었다. 이 서류는 기본 텍스트 추출 순서에서 표의 열 머리글이 값보다 **뒤에**
나온다. 머리글이 맨 끝에 몰려 찍히고 값은 그 앞에 따로 몰린다. 그 글에는 열이 남아
있지 않으니 모델이 맞출 방법이 없다.

`pymupdf` 의 정렬본(`get_text("text", sort=True)`)은 좌표 순으로 펴서 머리글 줄과 값 줄이
세로로 맞는다. AWB 쪽에는 이미 걸려 있던 것을 인보이스와 포장명세서로 넓혔다
(`TEXT_FIX["table_sort"]`, h1 에서만 켠다). 이것 하나로 열 뒤바뀜이 사라졌고, 수리
인보이스의 두 표를 둘 다 읽던 것도 같이 사라졌다.

기본으로 끄는 이유는 다른 판의 실측값이 기본 추출 글로 잰 값이기 때문이다. 조건으로
두면 그 차이도 숫자로 잴 수 있다.

## 5. 조용히 틀렸던 세 자리

셋 다 표는 멀쩡히 나오는데 값이 틀린 꼴이라 눈으로는 안 잡혔다. 시험으로 잠갔다.

1. **후처리가 줄 안의 글자를 전부 숫자로 바꿨다.** 예외가 `("description", "code")` 두
   이름으로 박혀 있었다. 인보이스 번호가 연도 네 자리가 되고, 앞에 0 이 붙은 PO 품목
   번호에서 0 이 날아갔다. 검증은 그대로 통과했다. 이름 목록을 지우고 스키마에 묻게
   바꿨다. 예전 판에서 글자 칸은 정확히 그 둘이라 하던 대로 돈다.
2. **나눠 부른 결과를 합칠 때 새 배열 둘이 `CAT_KEYS` 에 없었다.** 인보이스 네 장이 네
   번 답하는데 마지막 것만 남았다. 이어 붙이고 겹친 것을 뺀다.
3. **인보이스 줄과 포장명세서 줄을 품목 코드로만 이었다.** 열일곱 줄의 코드가 전부 같은
   서류에서 열여섯 줄이 짝을 잃었다. 인보이스 번호와 PO 와 PO 품목 번호까지 넣어 좁히고,
   같은 열쇠가 여러 줄이면 인쇄 순서대로 하나씩 쓴다.

## 6. 늘어난 검증

줄 단위 값은 합계만 봐서는 안 보인다. 금액 합이 맞아도 PO 가 다 비어 있을 수 있다.

| 이름 | 보는 것 |
|---|---|
| `ci_lines_po_no`, `pl_lines_po_no` | 줄마다 PO 번호가 있는가 |
| `ci_lines_code`, `pl_lines_code` | 줄마다 품목 코드가 하나라도 있는가 |
| `line_po_in_text` | 줄의 PO 번호가 원문에 있는가 |
| `po_list_vs_lines` | 헤더에 나열된 PO 와 줄에서 모은 PO 가 같은가 |
| `inv_total[번호]` | 인보이스 장마다 줄 합이 그 장의 총액과 같은가 |
| `ci_total_vs_invoices` | 장별 총액의 합이 전체 총액과 같은가 |
| `ci_pl_by_code` | 같은 품목 코드의 수량이 인보이스와 포장명세서에서 같은가 |

## 7. 실측

우시로 가는 두 건이다. 서류 원본과 실제 번호는 저장소에 없다.

| 케이스 | 쪽 | 인보이스 | 줄 | 검증 | 벽시계 |
|---|---|---|---|---|---|
| 텍스트, 여러 인보이스 | 11 | 4장 | 인보이스 17, 포장명세서 17 | OK 51 / WARN 1 / FAIL 1 | 약 25초 |
| 전면 스캔 | 4 | 1장 | 인보이스 1, 포장명세서 1 | OK 27 / WARN 5 / FAIL 0 | 약 16초 |

두 건 합쳐 41초, 모델 호출 여덟 번, API 환산 비용은 케이스당 2~3센트다.

읽는 법이 셋이다.

- 인보이스 네 장의 줄 합이 장마다 총액과 정확히 맞았고, 네 장의 합이 전체 총액과도
  맞았다. 줄을 빠뜨리거나 두 번 읽지 않았다는 뜻이다.
- 남은 FAIL 하나는 포장명세서와 운송장의 총중량이 다른 것이다. 서류 자체의 불일치라
  모델을 바꿔도 남는다. 그게 이 검증의 목적이다.
- 스캔 건에서 운송장에 적힌 PO 번호와 인보이스 줄의 PO 번호가 한 자리 달랐다. 스캔
  판독의 숫자 오독이고, `po_list_vs_lines` 가 잡았다. 스캔 쪽에는 원문 대조를 걸 글자가
  없어서 이런 자리는 교차 대조로만 드러난다.

## 8. 못 하는 것

- **Imp.Req. No.** 는 GERP 수입의뢰 쪽에서 오고 선적 서류에 인쇄되지 않는다. 여덟 열 중
  일곱을 서류에서 채우고 이 하나는 비워 둔다. 채운 척하면 받는 쪽이 그 값을 믿는다.
- **ETD 와 ETA** 는 스케줄에서 온다. 서류에 없다.
- **Forwarder** 는 하우스 운송장의 발행자 칸에 있는데 아직 안 뽑는다.
- **GERP 의 PO 품목에 실제로 잇는 일**은 여기서 하지 않는다. 이 표는 붙일 값을 정리해
  줄 뿐이고, 코드 체계가 맞는지는 하이닉스가 확인해야 한다(`02` 4장의 열린 질문 2번).

## 9. 데모 화면

상대에게 보여 주는 자리다. 켜면 바로 돌게 우시행 표본 서류를 걸어 두었다.

```bash
python3 tools/hynix_demo.py        # http://127.0.0.1:8766
```

왼쪽에서 표본을 누르거나 PDF 를 올리면 쪽을 가르고 서류별로 모델을 불러 품목 줄을
뽑는다. 진행이 단계별로 초와 함께 뜬다. 가운데에 GERP 품목 표가 그대로 나오고,
오른쪽에 선적 헤더와 숫자 검증과 원본 서류가 붙는다.

화면이 지키는 것이 셋이다.

1. **뽑은 값을 다 보여 준다.** 필수와 선택으로 접지 않는다. 그쪽이 쓰는 값이 우리 기준의
   「선택」 자리에 많다.
2. **사람이 고칠 수 있고, 고친 값이 그대로 엑셀로 나간다.** 칸을 눌러 적으면 그 줄에 연필
   표시가 붙고 내려받기에 반영된다. 고쳐도 안 담기면 확인 화면이 아니라 구경 화면이다.
   GERP 에서 채우는 `Imp.Req. No.` 도 여기서 적어 넣을 수 있다.
3. **어느 값이 서류 어디에서 왔는지 짚어 준다.** 줄을 누르면 오른쪽 원본의 그 자리에
   상자가 뜬다. 상대가 「이게 맞나」 를 확인하는 방법이 그것 말고 없다.

PO 번호나 품목 코드가 없어 자동으로 못 잇는 줄은 노란 바탕이고, GERP 에서 채우는 열은
회색이다. 숫자 검증은 맞음과 확인과 어긋남 셋으로 세고, 어긋난 자리만 아래에 풀어 적는다.

표본 서류는 `tools/hynix_demo.py` 의 `SAMPLES` 에 있다. 없는 것은 목록에서 빠지므로
서류 폴더가 없는 자리에서도 화면은 뜬다.

## 10. 쓰는 법

```bash
python3 tools/docpipe.py \
  --bundle 케이스이름=서류.pdf \
  --prompt h1 --claude-cli \
  --codes research/dt-automation/schema/codes.json \
  --save-full out.json
python3 tools/gerp_xlsx.py --pred out.json --out ~/Documents/kerol/out/gerp.xlsx
```

`--save` 는 모델이 낸 날것만 적는다. 표를 만드는 쪽은 검증 결과도 있어야 「검토」 시트를
채우므로 `--save-full` 을 쓴다. 날것만 주면 FAIL 이 하나도 없는 표가 나오고 조용히
통과한다.

엑셀 시트가 다섯이다. `BL Header`, `BL Item`, `인보이스`, `검토`, `읽는 법`. 마지막 시트에
어느 열이 서류에서 오고 어느 열이 GERP 에서 오는지 적어 두었다. PO 번호나 품목 코드가
비어 자동으로 못 잇는 줄은 노란 바탕이다. 사람이 그 줄만 본다.

결과 파일에는 서류 값이 들어가므로 저장소 밖에 둔다.
